# 规则

- 名称使用小写连字符，描述说明能力和适用任务；规则与说明使用中文，工具名称、配置键和代码保留原名。
- 从实际实践提炼职责、适用条件、关键约束、执行顺序和例外，写清在什么条件下做什么、需要保留什么；规则应足以指导判断与执行。
- 以表达完整、容易执行为准，不限定规则数量或每条长度。一条规则围绕一个判断或约束，关联条件一起说明，避免把多个职责塞进一句话或压成目标口号。
- 正文先集中列规则，再用一个 `## 示例` 章节展开具体做法。影响方案选择、行为边界和执行结果的条件留在规则区；具体命令、配置值、文件布局及用法放在示例中。
- 区分必须遵守的约束、推荐做法和可选方案，写明适用条件，不把几种方案同时列成必做步骤。
- 配置修改与安装、部署、数据操作的授权分别表述；只保留任务必要的执行顺序，不额外套通用的读取、验证和交付流程。
- 通用规则应有实际依据，不把参考项目的局部做法或示例参数升格成普遍要求；新增约束需有明确需求或可核验的技术原因。项目专用值留在项目配置或指令中。
- 示例按不同场景与边界充分覆盖，不限数量或篇幅。按实际使用顺序展开，用简短文案交代场景、前提与衔接，再展示需要的目录、配置、代码或前后对照，不只堆代码，也不合成长段落。
- 示例保留真实语法和关键逻辑，去掉业务名称、本机路径、专用地址和无关特例；相关文件名、导入、变量和配置保持一致。标明依赖、可选项和省略范围，不把骨架冒充完整实现，不将示例名称、布局和数量当作固定要求。
- 同一约定只维护一处，示例展示规则的应用，不换句话重述规则。细节在示例中展开，可复制的配置放在随附 assets 并说明用途，不另设 references，也不为不同示例类型另设章节。
- 优化时逐项核对原规则、配置、例外和示例，合并重复、删除过时内容，保留有独立意义的约束和用法；不为缩短篇幅删掉条件或把关键规则全部搬进示例。规则、正文说明与随附文件同步调整，避免互相矛盾。
- 技能源码平铺在技能库根目录，使用 `<技能名>/SKILL.md`；名称、源码目录、名称数组清单和发现链接保持一致，接入遵循 `skill-management`。

## 示例

名称和描述直接对应任务，例如 `module-testing` 描述为“编写模块行为测试，约定测试位置、运行环境和断言方式”，比“提升项目质量、规范开发流程”更容易判断何时使用。正文一级标题可写 `# 测试规则`，后接一个 `## 示例`。

下面区分技能源码与随附配置；`assets` 仅在需要可复制文件时创建，名称数组清单登记 `module-testing`：

```text
技能库根目录/
├── skills.json                       # ["module-testing"]
└── module-testing/
    ├── SKILL.md
    └── assets/
        └── vitest.config.ts           # 可选的配置模板
```

例如原规则包含“组件安装到共享 UI 包；安装前检查目录、别名和主题；比较已有文件，不默认覆盖；安装后核对生成文件与依赖”。压成“组件集中管理，保留已有修改”会丢失检查时机、冲突处理和完成条件，可以按行为拆开：

- 组件安装到共享 UI 包，执行前确认目标目录、导入别名与主题配置。
- 发现同名文件时先比较差异并保留已有修改，不直接覆盖。
- 安装后核对生成文件及依赖声明，确认消费方能正确引用。

对应示例再使用 `packages/ui` 展示文件归属、导入别名和同名文件的差异处理。目录名属于该示例，安装前后需要做的判断仍在规则中。

分支同步技能涉及不同权限与合并结果时，规则可以写“受保护分支通过 PR 更新；允许直接更新且无冲突时合并；发生冲突时转入冲突处理”。示例用表格展开，具体 API 参数放在随附工作流中：

| 场景 | 示例处理 |
| --- | --- |
| 目标分支受保护 | 创建或复用指向目标分支的同步 PR |
| 允许直接更新且合并成功 | 记录同步后的提交 |
| 合并发生冲突 | 保留源、目标 SHA，在同步分支解决冲突，不提交冲突标记 |

发布技能有 OIDC 和 Token 两种认证方案时，先写清选择条件，再分别链接配置；不要求两份工作流都安装。检查、构建、打包和完整性核验的共同约束集中说明，两种认证的凭据和权限差异各自展开。修改配置不代表执行实际发包。

从具体项目提炼配置时，例如固定地址 `https://internal.example.com` 改成输入 `SERVICE_URL`，需要保留“地址由哪一方提供、在哪一步读取”的说明；项目使用端口 3100、Node 24 或三个构建平台，并不能据此要求所有使用方采用同样的值。确实依赖某个运行时能力时，再说明该能力及版本条件。

可复制的完整工作流较长时，可放在 `assets/publish.yml`，正文链接该文件并说明触发事件、需要填写的变量和凭据、适用范围。正文中的步骤名、变量名和路径与文件保持一致；只展示片段时明确省略了什么。迁移要求若是“先保留兼容入口，再切换调用方”，这一顺序留在规则中，示例展示对应文件的改法。

下面是一个完整技能。任务较小，三条规则足以覆盖测试归属、验证目标和配置复用；复杂任务按实际条件补充规则，不以此作为数量模板。示例里的项目目录与上面的技能源码目录含义不同。

````markdown
---
name: module-testing
description: 编写模块行为测试，约定测试位置、运行环境和断言方式。
---

# 规则

- 测试放在源码旁，文件名使用 *.test.ts。
- 纯逻辑模块使用 Node 测试环境，断言公开返回值和错误行为。
- 测试与运行配置分开，不为了一个用例重复创建整套测试工程。

## 示例

测试与源码就近维护，共用一份运行配置。下面仅展示文件归属：

```text
项目根目录/
├── vitest.config.ts
└── src/
    ├── parseName.ts
    └── parseName.test.ts
```

使用 Vitest 的纯逻辑项目，在 `vitest.config.ts` 中选择 Node 环境，并扫描源码旁的测试：

```ts
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: {
    environment: "node",
    include: ["src/**/*.test.ts"],
  },
});
```

`parseName.ts` 去除名称两侧的空白，名称为空时抛错：

```ts
export const parseName = (value: string): string => {
  const name = value.trim();
  if (!name) throw new Error("名称不能为空");
  return name;
};
```

`parseName.test.ts` 通过公开函数断言这两项行为，不依赖内部实现：

```ts
import { expect, it } from "vitest";
import { parseName } from "./parseName";

it("去除名称两侧空白", () => {
  expect(parseName(" Alice ")).toBe("Alice");
});

it("拒绝空白名称", () => {
  expect(() => parseName(" ")).toThrow("名称不能为空");
});
```
````
